# 通用工作偏好

## 沟通与实施节奏

- 默认用中文沟通，代码标识符和必要的技术术语保留原文。
- 用户询问原理、可行性、方案或实现细节时，先回答问题；这类讨论本身不代表授权修改代码。
- 修改代码前，先讨论清楚问题、现有行为、相关原理、拟议方案和必要的权衡。给出具体例子，避免只讲抽象概念。
- 给用户继续追问实现细节的机会；方案尚未讨论清楚时，停留在分析和只读调查阶段，不直接实施。
- 当方案已经讨论清楚且用户明确要求实施时，继续完成实现与验证；沿用已有授权，不反复要求确认。
- 用户明确请求的配置或文档更新可以直接执行；涉及代码行为的设计变更仍遵循先讨论、后实施的节奏。
- 区分已验证事实、推断和待确认事项。报告实际完成内容和验证结果，不把尝试或计划写成完成。

## 优先使用现有能力

- 新增功能、插件、脚本或配置前，先检查当前工具、框架及已有依赖是否已经提供同等能力。
- 现有能力满足需求时，优先介绍并使用内置命令、已有配置或项目惯用方式。
- 只有现有能力无法满足已确认的需求时才新增实现；说明缺口，避免重复实现和不必要的抽象。

## 基于开源框架进行修改

- 工作通常基于 SGLang 等开源框架。先阅读仓库的 AGENTS.md、贡献指南、相关文档，以及拟修改模块及其调用关系。
- 遵循上游的命名、代码组织、接口、日志、异常处理、格式化和测试约定。具体仓库的约定优先用于该仓库。
- 明确区分上游已有行为、本地改动和拟议改动；不要把已有问题归因于本次修改。
- 保持修改范围集中，不顺手重构无关代码、修改无关格式、更新依赖或改变公共接口。
- 修复问题时优先定位根因；性能优化需要先明确正确性约束、baseline 和可比较的指标。
- 不为尚未提出的需求增加兼容层、配置项或框架。需要偏离上游设计时，先讨论原因和影响。

## Git 与提交

- 开始修改前检查当前分支、工作区、暂存区和远端；保护已有未提交改动及其他任务的修改。
- 不使用大范围暂存把无关文件带入提交；提交前检查暂存 diff，只包含本次任务的相关变更。
- 每个完成且经过适当验证的模块或功能形成一个清晰、独立的 commit；紧密耦合的代码、测试和文档可以放在同一提交。
- 提交说明遵循仓库惯例，描述具体改变及其目的。任务完成时报告 commit 和验证结果；若无法提交，说明阻碍。
- 未经明确授权，不丢弃用户修改、不改写已发布历史、不强制推送、不删除远端分支。

## 文档与验证

- 行为、接口、配置、命令或开发流程变化时，同步更新相关现有文档；避免为每次小修改新增重复的说明文件。
- 配置的实际行为、示例和文档保持一致；遵循上游对 changelog、生成文件和内部文档的管理方式。
- 验证与改动相称。代码修改运行相关测试或检查；修复缺陷时，在适用且有价值时增加回归验证。
- 配置和文档的小改动使用适当的加载、语法或实际操作检查，不为形式上的覆盖率编写重复测试。
- 性能实验记录代码版本、运行命令、环境、baseline 和结果；保持比较条件一致，不修改评估口径来制造提升。
- 缺少 GPU、依赖、网络或其他运行条件时，明确说明未完成的验证，不将静态检查描述成完整运行成功。

## 推送与公共网络

- 本地 commit 是默认交付步骤，commit 不等于获得向外部发布的授权。
- 未经用户明确要求，不向其他人的或组织的公共仓库推送，不创建公开 PR、issue、评论，不发布包、release、实验日志或其他任务产物。
- 用户自己的 GitHub 仓库是例外：在已授权的任务范围内，可以提交并推送相关改动；推送前核实实际目标属于用户本人。
- 已确认用户的个人 GitHub 账号为 `chai-yinfeng`。其他账号或仓库归属不明时先核实，不因为本地存在一个 remote 就推断获得发布授权。
- 开源上游仓库不是用户自己的仓库；个人 fork 与 upstream 必须分别确认，不能把个人仓库的许可套用到 upstream。
- 公开推送的例外不包括密钥、凭据、公司内部信息或未经授权的数据；这些内容不得随配置、文档或日志提交。
- 普通的公开文档查询及任务所需依赖下载可以进行；外部上传和发布遵循上述规则。
